# GIGVEYRO Backend — Security Documentation & Audit Policy

## 1. Secrets & Credentials Management
- Hardcoded secrets in production are strictly forbidden.
- `JWT_SECRET_KEY` must be configured via environment variables and possess a minimum length of 32 characters in production (`APP_ENV=production`).
- `TOTP_ENCRYPTION_KEY` must be a real generated Fernet key (`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`) in production — validated at startup in every environment (malformed key fails fast) and additionally checked against the `CHANGE_ME` placeholder in production.
- Database credentials must be provided via `DATABASE_URL`.

## 2. Payout Safety Configuration
- `PAYOUT_ENABLED` defaults to `False` in all environments.
- Private keys, mnemonics, or automated wallet signing code are strictly absent from the application codebase.
- Payout execution passes through explicit provider abstractions (`MockPayoutProvider` or `ExternalPayoutAdapter`) with safety checks.

## 3. Card Data Protection
- Payment card numbers are masked at the schema/API boundary.
- Plaintext full card numbers are never returned in public or owner endpoints.
- Known limitation: Database contains canonical digits for requisite uniqueness matching; encryption-at-rest is recommended for production database storage.

## 4. Middleware & Headers
- `SecurityHeadersMiddleware`: Sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy`.
- `RequestIDMiddleware`: Generates or propagates `X-Request-ID` for end-to-end request tracing.
- `RateLimitMiddleware`: Protects sensitive routes like `/auth/login` against brute-force attempts.
- Known limitation: `in_memory_rate_limiter` (`app/core/middleware.py`) keys on `request.client.host`, which is the proxy's address (not the real client) behind a reverse proxy unless `X-Forwarded-For` handling is added, and its counters are per-process — not shared across multiple workers. `REDIS_URL` is already configured (see infra settings) so the migration path is a Redis-backed sliding-window limiter using the same `is_rate_limited(key, max_requests, window_seconds)` interface; not implemented here as it is outside this stage's scope.

## 5. Authentication Sessions (V1.1)
- **Password hashing**: Argon2id via `pwdlib.PasswordHash.recommended()`. Login is constant-time regardless of whether the username exists (dummy-hash verify), so timing can't be used to enumerate accounts. Login/reset error messages never distinguish "unknown user" from "wrong password".
- **Access tokens**: JWT, HS256, `ACCESS_TOKEN_EXPIRE_MINUTES` (default 15 min), claims `sub`/`role`/`type`/`session_id`/`jti`/`exp`. `role` is never trusted from the token alone — every protected endpoint re-reads the account (and its `is_active` flag) from the database, and `require_roles` checks the DB-loaded role.
- **Refresh tokens & server-side sessions**: Every login creates an `AuthSession` row (`app/models/auth_session.py`). Only a SHA-256 hash of the refresh token is stored — never the plaintext token. `POST /auth/refresh` rotates the token in place on the same session row: the old token's hash is replaced, `rotation_counter` increments, and `last_used_at` updates. The session row lock (`SELECT ... FOR UPDATE`) makes concurrent refresh attempts on the same token serialize correctly — exactly one wins.
- **Reuse detection**: If a refresh token is presented whose hash no longer matches the session's current `refresh_token_hash` (i.e. it was already rotated away), the entire session is immediately revoked (`revoked_reason="reuse_detected"`) and the request is rejected with `409 Conflict`. This is intentionally strict — even two legitimate concurrent refreshes from the same client (e.g. two open tabs racing) will trip this and force re-login, since the system cannot distinguish that from an attacker replaying a stolen token. There is no grace-period exception in V1.1.
- **Immediate revocation on access tokens**: access tokens also carry `session_id`. `get_current_account` checks the session's `revoked_at`/`expires_at` on every request, so a revoked session (logout, logout-all, password reset, block) is rejected immediately rather than staying valid until the access token's natural 15-minute expiry. (Tokens minted without a `session_id`, e.g. bootstrap scripts, fall back to the pre-V1.1 account-only check.)
- **Logout**: `POST /auth/logout` revokes the session behind the given refresh token. Idempotent — an already-invalid or already-revoked token is treated as "nothing to do", never an error, so the response never discloses whether the token was valid.
- **Logout all devices**: `POST /auth/logout-all` (authenticated) revokes every active session for the caller's own account.
- **Session self-service**: `GET /auth/sessions` lists the caller's own active sessions (id, created/last-used/expires timestamps, a coarse device label, `is_current`) — never the token or its hash. `DELETE /auth/sessions/{id}` revokes one of the caller's own sessions; attempting to revoke another account's session returns `404` (not `403`, to avoid confirming the session id belongs to someone).
- **Password reset**: `AccountService.reset_password` (OWNER-only, `POST /owner/accounts/{id}/reset-password`) revokes every active session of the target account in the same call, so a compromised account can't stay logged in through the old password.
- **Block**: `AccountService.set_account_active(is_active=False)` also revokes every active session of the blocked account (in addition to the pre-existing `is_active` check that already rejects login/refresh/protected requests). Unblocking does **not** restore the revoked sessions — the user must log in again.
- **Session cleanup**: `AuthService.cleanup_expired_sessions()` deletes sessions expired more than `SESSION_CLEANUP_RETENTION_DAYS` (default 30) days ago. Not scheduled automatically — a production worker/cron must call it periodically.
- **Audit**: `auth.login`, `auth.logout`, `auth.logout_all`, and `auth.session_revoked` (reuse detection or explicit user revoke) are recorded via the existing `AuditService`/`AuditLog`. Passwords, tokens, and refresh-token hashes are never written to audit metadata.
- **CSRF**: The frontend BFF is cookie-based (`HttpOnly`, `SameSite=Lax`, `Secure` in production) and checks the `Origin` header on mutation routes when present. This is accepted as the V1.1 baseline; no separate CSRF token scheme was added, since `SameSite=Lax` already blocks cross-site form/script-initiated state-changing requests in modern browsers. If a future browser-compat reason requires it, the double-submit token pattern is the intended upgrade path.
- **2FA**: Not implemented in V1.1. OWNER accounts have no two-factor requirement yet — deferred to a follow-up stage after this session/rotation baseline is verified stable, per the project's staged-rollout policy.

## 6. Owner Two-Factor Authentication (V1.2)
- **Scope**: TOTP (RFC 6238), OWNER-only. The data model and services (`AccountTwoFactor`, `TwoFactorService`) are not OWNER-specific and could be opened to USER/MERCHANT later, but every `/auth/2fa/setup/*`, `/disable`, and `/recovery/regenerate` endpoint is gated with `require_roles(UserRole.OWNER)` in V1.2. No SMS fallback exists or is planned.
- **Secret storage**: the TOTP secret is encrypted at rest with Fernet (`app/core/totp_crypto.py`), keyed by `TOTP_ENCRYPTION_KEY`. Ciphertext is stored as `"<key_version>:<fernet_token>"` — a future key rotation adds a new version handler in `_fernet_for_version` without invalidating already-stored secrets. The plaintext secret is never logged; the confirmed secret is never returned by any endpoint after setup (`GET /auth/2fa/status` only ever returns `enabled`/`enabled_at`/`recovery_codes_remaining`).
- **Setup flow**: `POST /auth/2fa/setup/start` requires the OWNER's current password, generates a TOTP secret, and stores it in `PendingTwoFactorSetup` (separate table from the confirmed `AccountTwoFactor`) with a `TWO_FACTOR_SETUP_EXPIRE_MINUTES` (default 10) expiry. Starting a new setup replaces any existing pending row for that account, so abandoned setups don't accumulate. `POST /auth/2fa/setup/confirm` requires a valid 6-digit TOTP code against the pending secret; only then does `AccountTwoFactor` get created and 2FA become active. `TWO_FACTOR_REQUIRED` is never true for an account with only a pending (unconfirmed) setup.
- **QR / manual key**: `setup/start` returns a standard `otpauth://totp/GIGVEYRO:<username>?secret=...&issuer=GIGVEYRO` URI (compatible with Google/Microsoft Authenticator, 1Password, Authy-style TOTP apps) plus the same secret formatted as a manual-entry key. The QR image itself is rendered client-side (`qrcode` npm package) from the URI — the secret never leaves the browser/backend to a third-party QR service.
- **Login challenge**: for an account with 2FA enabled, `POST /auth/login` no longer returns tokens directly — it returns `{"two_factor_required": true, "challenge_token": ...}`. The challenge token is a purpose-specific JWT (`type=two_factor_challenge`, 5-minute TTL by default) whose `jti` is the id of a server-side `TwoFactorChallenge` row, so it can be consumed exactly once (row-locked via `SELECT ... FOR UPDATE`, same pattern as refresh-token rotation) and tracks its own `attempts` counter (locked out after `TWO_FACTOR_MAX_CHALLENGE_ATTEMPTS`, default 5). A challenge token cannot access any protected endpoint — `get_current_account` only accepts `type=access` tokens, so presenting a challenge token anywhere else is rejected with `401`. `POST /auth/2fa/verify` (challenge token + 6-digit TOTP or a recovery code) is the only way to actually mint a real session; a dead/expired/consumed/locked challenge returns `410 Gone` (restart login), while a live challenge with a wrong code returns `401` (retry).
- **Rate limiting**: `/auth/2fa/verify` is rate-limited per account id via the Redis-backed sliding-window limiter (`app/infra/redis_rate_limiter.py`, already built for this purpose), `TWO_FACTOR_VERIFY_RATE_LIMIT_REQUESTS`/`_WINDOW_SECONDS` (default 10 per 5 minutes). Fails open (allows the request) if Redis is unavailable, consistent with the rest of the app's documented rate-limiter posture — combined with the per-challenge attempt cap above, a single challenge can never be brute-forced regardless of Redis availability.
- **Recovery codes**: 10 codes generated on `setup/confirm` (format `XXXX-XXXX`, unambiguous alphabet), shown to the OWNER exactly once in the API response and never retrievable again. Only SHA-256 hashes are stored (`TwoFactorRecoveryCode.code_hash`); each row is marked `used_at` on first use and rejected on reuse. `POST /auth/2fa/recovery/regenerate` (password + TOTP required) deletes all existing codes and issues 10 new ones — the old codes stop working immediately.
- **Disable**: `POST /auth/2fa/disable` requires the current password **and** a valid TOTP or recovery code — a stolen browser session alone cannot turn off 2FA. On success, `AccountTwoFactor`, all recovery codes, and any pending setup are deleted.
- **Session revocation policy on enable/disable**: both enabling (`setup/confirm`) and disabling revoke every *other* active `AuthSession` for the account (via the existing `AuthService.logout_all(..., except_session_id=...)`, not duplicated) while leaving the session that performed the action intact. Rationale: sessions created before 2FA was turned on (or while it's being turned off) shouldn't silently outlive the security-state change.
- **OWNER enforcement**: `OWNER_2FA_REQUIRED` exists as a config flag (default `False`) but is **not yet wired to a blocking "setup required" login state** in V1.2 — an OWNER without 2FA configured can still log in normally even if the flag is `True`. This is a deliberate scope cut (a half-built enforcement gate that could lock out the bootstrap OWNER is worse than an honest gap) — see "Remaining gaps" in the V1.2 stage report. Enforcing it properly is the natural next step once this baseline has run in production for a while.
- **Password reset / block interaction**: OWNER's own password reset/change does not touch 2FA configuration (2FA and password are independent factors). Blocking an account already revokes its sessions (V1.1); the 2FA configuration itself is untouched by block/unblock, so an unblocked OWNER still needs their authenticator on the next login. No remote/admin "reset someone's 2FA" endpoint exists — a lost-device OWNER recovers via their own recovery codes, then reconfigures 2FA themselves after logging in.
- **Audit**: `auth.2fa_setup_started`, `auth.2fa_enabled`, `auth.2fa_disabled`, `auth.2fa_recovery_regenerated`, `auth.2fa_recovery_used`, `auth.2fa_login_success` are recorded via the existing `AuditService`. No per-failed-attempt audit spam — a challenge lockout is not separately audited beyond the `401`/`410` responses themselves (the per-challenge `attempts` counter already bounds this). TOTP secrets, QR URIs, TOTP codes, and recovery codes are never written to audit metadata or logs.
- **Notifications**: not integrated with the in-app notification system in V1.2 (that system is owned by another workstream) — flagged as a follow-up integration point, not built here.
